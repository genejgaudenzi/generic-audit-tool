# Repository standards

These standards govern repository changes. They are process policy, not implementation-specific coding standards. CI and repository-rule enforcement are intentionally deferred to later work.

## Decision authority and Product Vision alignment

The [Product Vision](../product/vision.md) is the highest-level product document. All implementation must align with it.

Repository Standards govern implementation practices, but do not supersede the Product Vision, requirements, or accepted [Architecture Decision Records](../decisions/README.md). If implementation conflicts with the Product Vision, revise the implementation or intentionally evolve the Product Vision first. Use the [project decision hierarchy](decision-hierarchy.md) to determine the owning layer for a decision and to preserve work-item traceability.

## Issue and branch workflow

Every change must be associated with a Linear issue unless a maintainer explicitly records an exemption in the pull request. Use the branch name generated by Linear for that issue.

Before implementation begins, the Linear issue must identify the Product Vision principles it supports, related requirements, and related accepted ADRs. Use the [standard implementation issue template](decision-hierarchy.md#standard-linear-implementation-issue-template). Every implementation issue must trace back to both the Product Vision and applicable accepted ADRs; if no ADR applies, record `None` and explain why.

Use the existing scripts to keep branch handling consistent:

- [`scripts/start_branch.sh`](../../scripts/start_branch.sh) creates a branch from the current default branch and pushes it. For example: `scripts/start_branch.sh GEN-7 repository-standards-tooling`.
- [`scripts/finish_branch.sh`](../../scripts/finish_branch.sh) verifies a merged pull request, updates the default branch, and removes the completed local branch. Run it only from the merged feature branch.

Do not reuse an issue branch for unrelated work. Keep a branch and pull request focused on the issue it names.

## Commits and pull requests

Use clear, focused commits that explain the change. A commit may contain related updates needed to keep one change coherent; do not split work merely to increase commit count.

Open pull requests against `main`. A pull request must:

- name or link its Linear issue, or state the approved exemption;
- identify the Product Vision principles, related requirements, and related ADRs that govern the work;
- describe the user or repository impact and keep its scope limited to that issue;
- identify validation performed and any checks not run, with a reason;
- call out dependency, generated-file, documentation, or release-note effects; and
- use the repository pull-request template where available.

Reviewers should confirm issue scope, policy compliance, validation evidence, and whether follow-up work is clearly identified. Author and reviewer responsibilities do not replace future protected-branch controls.

## Required local pre-merge checks

Before requesting review, run the current project checks from the [development environment guide](../development.md):

```bash
uv lock --check
uv run ruff format --check .
uv run ruff check .
uv run pyright
uv run pytest
```

Also run `git diff --check` and review the staged diff. A change that cannot run a required check must explain why in the pull request.

These are the current local expectations, not a CI requirement. Automated enforcement and any changes to the check set are deferred.

## Repository hygiene

- Do not commit generated output, local environments, caches, credentials, tokens, private keys, or machine-specific paths. Follow [`.gitignore`](../../.gitignore); extend it only for deliberate local artifacts.
- Add dependencies only when necessary for the issue. Record the rationale and lockfile impact in the pull request. Update `uv.lock` whenever dependency resolution changes.
- Do not add large binaries to the repository unless they are essential, have maintainer approval, and the pull request records their purpose, source, size, and retention need. Prefer an external, documented distribution location when practical.
- Never place secrets in source, documentation examples, configuration, issue comments, or pull requests. Revoke exposed credentials and report the exposure through the project’s approved security channel.

## Change and release notes

Keep change notes lightweight. Include a release-note entry in the pull request only when a change affects users, contributors, compatibility, configuration, or documented behavior. For internal-only changes, state `No release note required` in the pull request. Release publication and automation are out of scope for these standards.

## Future repository protection policy

The intended future configuration for `main` is protected-branch review with required passing checks, no direct pushes, and a documented exception path. These controls are policy only and are **not yet enforced** by GitHub settings or CI. Until they are implemented, contributors and reviewers must apply this document manually.

No standalone Definition of Done or Coding Standards document currently exists in the tracked repository. This document establishes repository-process expectations only; future coding standards must be introduced separately and must not conflict with this policy.
